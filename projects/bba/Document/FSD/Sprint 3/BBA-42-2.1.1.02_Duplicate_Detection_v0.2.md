# 2. Purpose and Context

This FRS specifies the requirements for detecting and handling duplicate records when a Lead is manually created or edited in the CRM, a Lead is created through the API, or an Enquiry is created. It aims to prevent duplicate Lead and Enquiry records under the defined rules and route each result to the appropriate handling flow for the record type and intake channel.

The Lead and Enquiry comparison scopes, duplicate criteria, and result handling are specified in the User Stories and corresponding rules in this document.

|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Duplicate checking for Leads manually created in the CRM, created through the API, and manually edited in the CRM; system-wide Lead search; exclusion of Inactive Leads and Leads Closed longer than the threshold configured by Brand and Centre (currently more than 3 years); comparison of Lead records only, not Child records; application of normalization and blank-value rules; and duplicate checking for Enquiries belonging to the identified Lead, excluding Inactive and Closed Enquiries. | Comparison of Child records; phone number comparison; automatic merging, deletion, or inactivation of Leads; creating a Reference Log for a manually created or edited Lead; automatically sharing a Centre when a Lead edit causes a duplicate; handling duplicates detected after Lead creation; Contact duplicate logic; the Centre Sharing access-provisioning process after a request is received; detailed API responses for duplicate Enquiries; rollback, retry, locking, reconciliation, or recovery for concurrent requests. |

# 6. Functional Requirements by User Story

## 6.1 BBA-42: US-001 - Detect Duplicate Leads on Create or Edit

### User Story

As a CRM user or API channel, I want every Lead create or edit request to be checked consistently for duplicates so that duplicate Leads are prevented and the correct handling is applied based on status, Centre, and intake channel.

### Functional Requirement

| FR ID  | Functional Requirement                                                                                                                                                                                                                                                           |
|--------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| FR-001 | The system must check for duplicates before completing a request to manually create a Lead in the CRM, manually edit a Lead in the CRM, or create a Lead through the API, according to this document’s scope and comparison rules.                                               |
| FR-002 | If no duplicate Lead is found, the system allows the create or edit flow to continue. If an API request matches an existing Lead, the system does not create a new Lead and handles the result according to the applicable Reference Log, Lead status, and Centre Sharing rules. |

### Main Functional Flow

1\. A user or API client submits a Lead create or edit request.

2\. The system checks Leads across the entire system and excludes Inactive Leads and Leads that have been Closed longer than the configured threshold (currently more than 3 years) from comparison (BR-007, BR-012–BR-014; VAL-002, VAL-009–VAL-010).

3\. The system normalizes Lead Full Name, Email, and Date of Birth according to BR-011 and VAL-008.

4\. The system identifies a duplicate Lead when Lead Full Name matches together with Email, or when Lead Full Name matches together with Date of Birth (BR-003). Blank values and individual comparison outcomes are handled according to VAL-003–VAL-007.

5\. The system returns either no duplicate result or one in-scope duplicate Lead.

6\. The system hands the result off to the corresponding manual or API handling flow.

### Alternative Functional Flow

1\. No duplicate Lead is found: the owning Lead create or edit flow continues.

2\. Email or Date of Birth is blank in either record: that value is treated as different.

3\. Email values differ, but Lead Full Name and Date of Birth match: the records are considered duplicates based on Lead Full Name + Date of Birth.

4\. An Inactive Lead or a Lead Closed longer than the configured threshold (currently more than 3 years) is excluded; the owning flow continues.

### Exception Flow

1\. Lead data is invalid or incomplete: apply the Lead function’s validation before completing duplicate processing.

### Business Rules

| BR ID  | Rule                                                                                                                                                                                        |
|--------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BR-001 | Every manual Lead creation, manual Lead edit, and API Lead creation request must be checked before completion.                                                                              |
| BR-002 | Only Lead records are compared; Child records are not searched or compared.                                                                                                                 |
| BR-003 | A Lead is a duplicate when Lead Full Name matches together with Email, or when Lead Full Name matches together with Date of Birth.                                                          |
| BR-004 | A duplicate found during creation does not result in a new Lead being created.                                                                                                              |
| BR-005 | If no Lead matches the approved duplicate rules, the Lead creation flow may continue.                                                                                                       |
| BR-006 | BBA-42 does not merge, delete, or automatically inactivate a Lead. A Closed Lead is changed to New only in the specified API or manual Lead creation scenarios.                             |
| BR-007 | Lead duplicate detection is performed across the entire system, with no restriction by Centre, country, or Brand.                                                                           |
| BR-008 | An API request that matches an existing Lead must have a Reference Log recording the source, campaign, and Centre supplied in the request.                                                  |
| BR-009 | Do not create a Reference Log when a duplicate is found during manual Lead creation or editing.                                                                                             |
| BR-010 | No more than one Lead within the comparison scope may satisfy the approved duplicate rules.                                                                                                 |
| BR-011 | Text comparisons are case-insensitive, ignore Vietnamese diacritics, and trim leading and trailing spaces. Date of Birth uses the dd/mm/yyyy format. A blank value is treated as different. |
| BR-012 | Inactive Leads are excluded from the comparison scope.                                                                                                                                      |
| BR-013 | A Lead Closed longer than the configured threshold is excluded. The current threshold is 3 years; a Lead Closed for exactly 3 years remains in scope.                                       |
| BR-014 | The Closed-duration threshold is configurable by Brand and Centre.                                                                                                                          |
| BR-015 | When an API Lead creation request matches a Closed Lead still within the threshold, no new Lead is created and the existing Lead is reopened from Closed to New.                            |
| BR-016 | When an API Lead creation request matches a Lead that is not Closed, no new Lead is created and the existing Lead status remains unchanged.                                                 |
| BR-017 | For an API duplicate Lead, compare the requesting Centre with the Centre Sharing list. If the Centre is already listed, leave the list unchanged; otherwise, add it according to BBA-41.    |
| BR-018 | Reopening a Lead does not delete its existing care history, Timeline Activities, or audit records.                                                                                          |

## 6.2 BBA-42: US-002 - Handle Duplicate Lead Results for Manual CRM Operations

### User Story

As a CRM user, I want the system to display duplicate Leads and provide actions appropriate to the create or edit operation, Lead status, and Centre so that duplicate records and unauthorised Centre sharing are avoided.

### Functional Requirement

| FR ID  | Functional Requirement                                                                                                                                                                                                                                                                                                                                                 |
|--------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| FR-003 | When a manual operation detects a duplicate Lead, the CRM must display the result for the user to select an appropriate action. Displayed fields and data masking must follow the current UI components and access permissions.                                                                                                                                        |
| FR-004 | When manual Lead creation detects a duplicate, the CRM must display the actions permitted by the duplicate Lead’s status and the requesting Centre. The selected action must handle the existing Lead and apply the corresponding Centre Sharing rule; no new Lead or manual Reference Log is created.                                                                 |
| FR-005 | When a manual Lead edit detects a duplicate, the system must block the save. If the duplicate Lead belongs to another Centre, the CRM provides Cancel or Send Request to Share Centre. After the user confirms the request, the system sends a notification according to BR-025. Sending the request does not save the Lead changes or automatically share the Centre. |

### Main Functional Flow

1\. The system receives the duplicate Lead result from US-001.

2\. The system masks result data according to current access permissions.

3\. The system determines whether the operation is a create or edit, the duplicate Lead’s status, and the requesting Centre.

4\. For a manual create that matches a Lead that is not Closed, the user selects Cancel or Save.

5\. Save uses the existing Lead; it does not create a Lead or Reference Log and applies Centre Sharing according to the same-Centre or cross-Centre rule.

### Alternative Functional Flow

1\. A manual create matches a Closed Lead that is still within the threshold: Cancel leaves it Closed; Reopen Lead changes the existing Lead to New and then applies Centre Sharing.

2\. A manual create matches a Lead that is not Closed: Cancel makes no changes; Save uses the existing Lead, keeps its status, and applies Centre Sharing.

3\. A manual edit matches a Lead in the same Centre: only Cancel is available; the changes are not saved.

4\. A manual edit matches a Lead in another Centre: the user selects Cancel or Send Request to Share Centre. If the user confirms the request, the system sends a notification to the Head of Brand according to BR-025. The Lead changes are discarded; the request does not automatically grant access or share the Centre.

### Exception Flow

1\. When a manual edit causes a cross-Centre duplicate, saving is blocked. If the user selects and confirms Send Request to Share Centre, the system sends an in-system notification to the Head of Brand according to BR-025. The Lead changes are discarded; the request does not automatically grant access or share the Centre.

2\. Errors when saving Centre Sharing are handled by BBA-41 and the owning platform process.

## 6.3 BBA-42: US-003 - Prevent Duplicate Enquiry Creation

### User Story

As a CRM user or API channel, I want the system to prevent duplicate Enquiries for the same Lead and the same enquiry details.

### Functional Requirement

| FR ID  | Functional Requirement                                                                                                                                                                                                         |
|--------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| FR-006 | When creating an Enquiry, the system must check for duplicates among Enquiries belonging to the identified Lead, according to this document’s Enquiry scope and comparison rules.                                              |
| FR-007 | If a duplicate Enquiry is found, the system does not create a new Enquiry. In the CRM, the system displays the duplicate Enquiry and allows only cancellation; API requests are handled according to the applicable API rules. |
| FR-008 | If no duplicate Enquiry is found, the system allows the Enquiry creation flow to continue.                                                                                                                                     |

### Main Functional Flow

1\. The system receives an Enquiry create request for an identified Lead.

2\. The system searches for Enquiries belonging to that Lead and excludes Inactive or Closed Enquiries from the comparison set.

3\. The system compares Brand, Campus, Preferred Level, Start Date, and Session.

4\. If all five values match a valid Enquiry, the system identifies a duplicate Enquiry.

5\. In the CRM, the system displays the duplicate Enquiry with Cancel as the only action; through the API, the system does not create a new Enquiry.

6\. When the user selects Cancel in the CRM, the system does not create the Enquiry.

### Alternative Functional Flow

1\. At least one value differs: the Enquiry is not identified as a duplicate, and the Enquiry creation flow may continue.

2\. A comparison field is blank: that field is treated as different.

3\. Inactive or Closed Enquiries are excluded; an Enquiry belonging to another Lead is not considered a duplicate of the current Lead.

### Exception Flow

1\. Recovery handling when a search or save fails belongs to the owning function.

2\. Enquiry data is invalid or incomplete: apply the Enquiry function’s validation before duplicate processing.

# 7. Appendix and Glossary

## 7.1 Glossary

| Term                   | Definition in this FRS                                                                                                                                                                               |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Duplicate Lead         | A Lead in the comparison scope whose normalized Lead Full Name + Email or Lead Full Name + Date of Birth matches. Inactive Leads and Leads Closed longer than the configured threshold are excluded. |
| Same-Centre Duplicate  | A duplicate Lead that already has the requesting Centre in its Centre Sharing list.                                                                                                                  |
| Cross-Centre Duplicate | A duplicate Lead that does not yet have the requesting Centre in its Centre Sharing list.                                                                                                            |
| Reference Log          | An intake record for an API duplicate Lead that stores the source, campaign, and Centre. BBA-42 does not create a Reference Log for manual Lead creation or editing.                                 |
| Masked Value           | A value in a manual result that is hidden according to the user’s current role and data scope.                                                                                                       |
| Duplicate Enquiry      | An Enquiry for the same Lead with matching Brand, Campus, Preferred Level, Start Date, and Session; Inactive and Closed Enquiries are excluded from comparison.                                      |
